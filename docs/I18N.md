# I18N.md — Internationalization & Localization

> How copy is sourced and how locales are routed. Audience: LLM agents and developers who need to know where a string comes from before changing it, and what it takes to add a language.

---

## 1. Overview — TL;DR

**The project is multi-locale by construction; the routed languages are whatever the OneEntry project has active (`en_US` + `de_DE` today).**

- Routing lives under `app/[locale]/`, with an **as-needed prefix scheme**: the default locale has no prefix (`/cart`), every other locale is prefixed (`/de/cart`). Existing English URLs — and their rankings — are untouched when a second locale is switched on.
- The active list comes from the project settings (OE → Settings → Localization), snapshotted at build time into [locales.generated.ts](../src/lib/oneentry/locales.generated.ts) by `.claude/temp/gen-locales.mjs`. It is a snapshot rather than a live lookup because [proxy.ts](../proxy.ts) runs at the edge on every request and `generateStaticParams` runs at build time — neither can call OneEntry. The generated file is committed, so a build with no CMS reachable still routes what shipped last.
- **The default locale is not part of that snapshot.** It decides which language owns the un-prefixed URLs, so it is the `DEFAULT_LOCALE` constant in [locale.ts](../src/lib/oneentry/locale.ts) — reordering languages in the admin panel must not be able to move every indexed URL on the site.
- **All UI copy is admin-editable.** Every user-facing string resolves through one flat CMS dictionary; the constants a component passes to `useT` / `useDict` are offline fallbacks, not the source.
- **A fallback lives in the file whose JSX renders it** — always, with no shared copy module in between. Two components that show the same phrase each declare it; the OE marker, not an import, is what keeps them in step. `src/app/data/` no longer holds copy at all; what remains there is configuration and data (see §3.3).

Enabling a locale: localise the content in the admin panel → rebuild. `npm run gen:locales` runs automatically before `dev` and `build`, and routing, `generateStaticParams`, hreflang alternates and the switcher all read the same list.

## 2. Locale model

[src/lib/oneentry/locale.ts](../src/lib/oneentry/locale.ts) is the single source of truth. Two spellings of the same thing travel through the app:

| Kind | Example | Used by |
|---|---|---|
| **CMS code** (`CmsLocaleCode`) | `en_US`, `fr_FR` | every SDK call (`langCode`) |
| **Short code** (`ShortLocaleCode`) | `en`, `fr` | the URL segment, `<html lang>`, hreflang |

| Export | Purpose |
|---|---|
| `DEFAULT_LOCALE` | The unprefixed locale. A constant — changing it moves every indexed URL, so it takes a code review. |
| `CMS_LOCALES` | Every routed locale, default first. Built from `GENERATED_CMS_LOCALES` (the project-settings snapshot). |
| `toShortCode` / `toCmsCode` | Convert between the two spellings. |
| `buildLanguageAlternates` | hreflang map for a route — used by `withCmsSeo`. |

Server components read the active locale from the route segment via `currentCmsLocale()` ([current-locale.ts](../src/lib/oneentry/current-locale.ts)). **Root params are Server-Component-only**: Server Actions and Route Handlers must take the locale as an argument instead.

### 2.1 How a loader gets its locale

Three shapes, and the difference matters:

| Shape | Rule |
|---|---|
| Plain loader / React `cache()` | `const lang = langArg ?? (await currentCmsLocale())`. Root params are readable here, so a page never has to pass `lang`. |
| `unstable_cache`d body | Root params are **not** readable inside — `currentCmsLocale()` would silently return the default. The locale must arrive as an argument, which also keys the cache entry per language. |
| SDK call with no `langCode` parameter | `Blocks.getSlides` is the case in practice: the response language comes from the instance, not the call. Use `getApiForLang(lang)` ([index.ts](../src/lib/oneentry/index.ts)) — it hands out a lazily-created, app-token-only instance per locale. Never re-point the singleton: on the server it is shared by every visitor, in the browser it carries the shopper's session. |

Content read out of a raw OE payload (`localizeInfos`, per-locale `attributeValues` slices) should try the rendering locale first and `DEFAULT_LOCALE` second, so an untranslated block keeps its English heading instead of rendering blank.

## 3. Where copy comes from

One flat dictionary, loaded once per request tree.

```text
OE attribute sets (44)  →  getDictionary()  →  <DictProvider>  →  useT / useDict / useList
        │                       │
        │                       └─ server-side readers call getSystemSet / t() directly
        └─ marker → value, flattened; markers are unique tenant-wide
```

| Layer | File | Notes |
|---|---|---|
| Set list | [dictionary.ts](../src/lib/oneentry/dictionary.ts) `DICTIONARY_SET_MARKERS` | Explicit, because the public `attributes-sets` endpoint ignores `offset`/`limit` and only ever returns the first 10 of the tenant's sets. |
| Loader | `getDictionary(lang?)` | Fetches every marker in parallel, TTL-cached 5 min per process. Never throws — an unreachable CMS yields `{}` and every call site falls back to its shipped copy. |
| Provider | [DictContext.tsx](../src/lib/oneentry/labels/DictContext.tsx) | One `DictProvider` in the root layout. The per-screen label providers this document used to describe are gone. |
| Readers | `useT(marker, fallback)`, `useDict(prefix, OBJECT)`, `useList(marker, array)` | `useT` for one string; `useDict` overlays a whole label object (`prefix + snake_case(key)`); `useList` splits a CSV. |
| Server readers | `t(marker, key, fallback, lang)`, `se(key)` | For RSC / Server Actions. `product_specs` and `server_errors` are read this way and stay out of the client dictionary. |

**Naming convention** ([dict.ts](../src/lib/oneentry/labels/dict.ts)): `useDict('checkout_delivery_', LABELS)` reads `checkout_delivery_<snake_case_key>` for every **string** in `LABELS`. Non-string entries (option arrays, nested maps) pass through untouched — they are structure, not copy; a nested map that *is* copy gets its own overlay (see `service_maintenance_category_`).

**Where the fallback lives.** In the file that renders it:

```tsx
// src/app/pages/account/myData/AccountDeletionSection.tsx
export const ACCOUNT_DELETION_LABELS = {
  title: 'Account Deletion',
  ctaDelete: 'Delete Account',
} as const;

export function AccountDeletionSection() {
  const L = useDict('user_account_deletion_', ACCOUNT_DELETION_LABELS);
```

The phrase and the JSX that shows it are one screenful apart, so changing copy means opening one file. Rules:

| Readers | Where the constant goes |
|---|---|
| One component | That component's own file, `export const` (exported so tests and the fill tooling can import it). |
| Several components | One constant per reader, each holding only the keys that reader renders. Copy is duplicated across the files on purpose — never re-exported from a shared module. |

**Why duplicate rather than share.** The wording on screen comes from OE, so two files holding the same default both resolve through the same marker and cannot drift where a shopper would see it. What sharing bought — one place to edit — the admin panel already provides; what it cost was a component reaching across features for a phrase (`ProductCard` importing catalog copy, `lib/` importing from `pages/`) and label objects that kept keys no caller rendered. Keep duplicated fallbacks byte-identical; a diverging default shows up only when the CMS is unreachable, which is exactly when nobody is looking.

Where a subset would break a type — `SORT_OPTIONS[].labelKey` indexing into a label object — the *key union* is shared and the wording is not: [`CatalogTemplate.types.ts`](../src/app/components/catalog/CatalogTemplate.types.ts) exports `SortLabelKey`, and each renderer's own object is declared `satisfies Record<SortLabelKey, string>`, so dropping a key is still a compile error.

It is a plain `const`, not a literal inlined into the `useDict` argument: `mergeDict` returns the same object when the CMS overrode nothing, and that stable identity is what keeps `useMemo` downstream from churning on every render. An exported constant is also what the marker tooling reads.

**Prefer one `useDict` over a column of `useT`.** A screen with two dozen labels reads better as a single overlay, and the swap is free when the key names are chosen so that `prefix + snake_case(key)` lands on the marker OE already holds — `payOnDelivery` → `checkout_payment_pay_on_delivery`. Where a marker cannot be reached that way (`footer_support_1_title` would need the key `support_1_title`), rename it in the CMS with [`admin-rename-markers.mjs`](../.claude/temp/admin-rename-markers.mjs), which copies the authored value across and deletes the old attribute.

**A per-reader constant shrinks the registry to what is actually read.** A whole-object overlay used to register every key in the shared object, including keys that renderer never touched — `useDict('product_card_actions_', PRODUCT_ACTION_LABELS)` in `QuickViewModal` created 23 markers for the 5 strings it showed, and the PDP read the same wording through its own `product-card-*` markers instead. Splitting the objects dropped 27 such markers (`product_card_actions_size_guide`, `product_card_breadcrumb_view_all`, `interface_controls_view_new_in`, …). None of them had a reader in the code, so nothing on screen changed; any attribute an editor already authored under those names in OE is simply an orphan, as it always was.

**The call sites are the registry.** [`dict-extract.mjs`](../.claude/temp/dict-extract.mjs) parses every `useDict` / `mergeDict` out of the TypeScript AST and prints the markers each one reads; [`admin-fill-dicts.mjs`](../.claude/temp/admin-fill-dicts.mjs) creates them in OneEntry from that list. Nothing is hand-maintained, so a new overlay cannot be forgotten — it can only be missing a set in that script's `PREFIX_SETS` table, which it reports by name.

### 3.1 Strings with a runtime value

An admin-authored string cannot interpolate, and a `{` or `}` in an attribute value makes OneEntry's public read of the **entire set** fail with a JSON cast error. Both constraints are solved the same way: `%token%` placeholders filled by [fillTokens](../src/app/utils/fillTokens.ts).

```ts
const label = useT('interface_controls_page_of', CATALOG_PAGINATION_LABELS.pageOf);
fillTokens(label, { current: 3, total: 12 }); // "Page 3 of 12"
```

Unknown tokens are left visible (`%typo%`) rather than blanked, so an admin-side typo is obvious.

### 3.2 Form copy is a different mechanism

A form field's copy belongs to the **form entity**, not to a system-text set: `localizeInfos.title` for the label, `additionalFields` for placeholder / helper / mask / options, plus the form's own `successMessage` / `unsuccessMessage`. Read it with `useFormLabel` / `useFormPlaceholder` / `useFormMessage` / `useFormOptions` ([placeholders.ts](../src/lib/oneentry/forms/placeholders.ts)). See [HARDCODED_TEXTS.md](../.claude/temp/HARDCODED_TEXTS.md) §3 for which screens own which form.

### 3.3 What is deliberately still in code

| Kind | Example | Why |
|---|---|---|
| Lookup tables | `HEX_COLOR_NAMES`, `FILTER_GROUP_KEY` in `clothing-filter.ts` | Only ever read *inverted*, to resolve an OE-supplied string to an internal key. The rendered label already comes from OE; making these editable would let an admin break filtering. |
| Stable option keys | `DISCOUNT_BUCKET_KEYS`, `SORT_OPTIONS[].value` | The value is code-owned, the wording is admin-editable. Matching on a label that an editor can reword is the bug this split prevents. |
| Routes and hrefs | `STEP_ROUTES`, `ctaHomeHref` | Navigation, not copy. |
| Brand names | `Apple Pay`, `PAYMENT_METHOD_NAMES`, social network names | Payment-scheme / platform names, keys of an icon map. |
| Data fixtures | `SIZE_DROPDOWN_LABELS.clothingSizes`, `defaultSku` | Sizes and identifiers, not wording. |
| Measurement tables | `SIZE_GUIDE_DATA`, `QUICK_VIEW_SIZE_DATA` in [sizeGuide.ts](../src/app/data/sizeGuide.ts) | Editable in OE as pipe-separated rows (`size_guide_rows`), but the shipped table is data, so it stays in `src/app/data/` where the fill tooling can read it without importing a component. |
| `NEWSLETTER_FORM_LABELS.notConfigured` | Shown exactly when OE has no `subscribe_new_drops` form | Could never be read from the thing that is missing. |
| Brace placeholders | `VALIDATION_MESSAGES.tooShort` (`Must be at least {min} characters`) | `{` / `}` in an attribute value breaks OneEntry's public read of the whole set, so these two stay code-only; the number comes from the OE form validator at render time. |

## 4. Adding a locale

1. Activate the language in OE → Settings → Localization.
2. Localise content in the admin panel: products, pages, blocks, **and every attribute set** — an unlocalised set falls back to `en_US`.
3. Rebuild (`npm run build` regenerates the snapshot first when the generator is present; `npm run gen:locales` does it on its own). Routing, `generateStaticParams`, hreflang alternates and the locale switcher all pick it up. Commit the regenerated [locales.generated.ts](../src/lib/oneentry/locales.generated.ts) — the deploy build may not have CMS access.
4. Check the two things that are not yet locale-derived:
   - **Currency** — [currencyConfig.ts](../src/app/data/currencyConfig.ts) is frozen to USD (`CURRENCY.format`), aligned with `seoData.ts` for Merchant/Catalog validation. A second currency needs `Intl.NumberFormat(locale, …)` and an OE-side price per locale.
   - **Date formatting** — a handful of `toLocaleDateString('en-GB', …)` / `Intl.DateTimeFormat('en-US', …)` seeds (checkout confirmation, account orders, review dates, sale countdown). Thread the active locale through when a second language ships.

## 5. What is intentionally NOT implemented

- No `next-intl` / `react-intl` / `next-i18next` — copy comes from OneEntry, not a local JSON catalogue.
- No RTL support (no `dir="rtl"` handling, no `rtl:` variants).
- No pluralisation library — the few pluralised strings use separate singular/plural markers (`your_bag_item_singular` / `_plural`).
- No currency conversion, no imperial/metric conversion.
